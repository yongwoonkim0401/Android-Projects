# SciCalc — 안드로이드 공학용 계산기

수식이 길어져도 메모리를 적게 쓰고, 입력 버퍼 크기 때문에 앱이 죽거나 느려지지 않는 것을
설계의 1순위로 둔 계산기입니다. 핵심은 **문자열을 다시 만들지 않는 입력 버퍼**와
**재귀 없는 스택 기반 파싱/계산**입니다.

## 설계 요약

| 문제 | 흔한 구현 | 이 앱의 방식 | 효과 |
|---|---|---|---|
| 키 입력마다 수식 문자열 재생성 | `text = text + "5"` | 갭 버퍼(`CharArray` 1개) | 입력당 O(1), 할당 0 |
| 토큰을 객체 리스트로 | `List<Token>` | 병렬 배열(`IntArray`/`DoubleArray`) | 객체 0개, 재사용 |
| 재귀 하강 파서 | 괄호 깊이 = 콜스택 깊이 | 조차장(shunting-yard) + 힙 스택 | StackOverflow 불가 |
| 계산 스택에 박싱 | `Stack<Double>` | `DoubleStack` | 박싱 0 |
| 긴 수식 전체를 TextView 에 | `setText(전체)` | 커서 주변 윈도우만 렌더 | 렌더 비용 일정 |
| UI 스레드에서 파싱 | 항상 동기 계산 | 길면 디바운스 + 워커 | 입력 지연 없음 |

### 1. 입력 버퍼 — 갭 버퍼

`core/GapBuffer.kt`

```
[ 커서 앞 ][      갭      ][ 커서 뒤 ]
0      gapStart        gapEnd    size
```

커서 위치에 빈 공간을 두고 삽입은 갭을 한 칸 먹고, 삭제는 한 칸 되돌립니다.
둘 다 O(1) 이고 **할당이 없습니다**. 배열이 모자랄 때만 1.5 배로 늘리므로
삽입 한 번의 분할상환 비용도 O(1) 입니다.

문자열 이어붙이기 방식은 n 자를 입력하는 동안 누적 O(n²) 바이트를 할당하고 그만큼 GC 쓰레기를
만듭니다. 5,000 자 수식이면 수십 MB 가 쓰레기로 지나가면서 GC 가 입력 프레임을 잡아먹습니다.
갭 버퍼는 10 만 자를 넣어도 실제 메모리가 `CharArray` 하나(약 200KB)뿐입니다.

`AC`(clear)는 갭만 되돌리는 O(1) 연산이고, 배열이 과도하게 커진 경우에만 이때 회수합니다.

### 2. 파싱 — 조차장 알고리즘

`core/Tokenizer.kt` → `core/ShuntingYard.kt` → `core/RpnEvaluator.kt`

1. **토크나이저**가 버퍼를 인덱스로만 훑어 토큰을 뽑습니다. `substring` 도 `toString()` 도
   호출하지 않습니다. 숫자는 문자에서 곧바로 `double` 로 누적하되,
   가수가 2⁵³ 이하이고 지수가 ±22 이내면 `Double.parseDouble` 과 비트 단위로 같은 결과를 냅니다.
2. **조차장 알고리즘**이 중위 → 후위(RPN)로 바꿉니다. 괄호 중첩은 콜스택이 아니라
   힙의 `IntStack` 깊이로 표현됩니다. 그래서 괄호를 5,000 겹 넣어도 콜스택은 한 프레임뿐입니다.
3. **RPN 평가기**가 `DoubleStack` 하나로 앞에서 뒤로 한 번 훑어 계산합니다.

세 단계 모두 내부 배열을 재사용합니다. 배열이 필요한 크기까지 자란 뒤에는
**같은 수식을 몇 번을 계산해도 힙 할당이 0** 입니다.

한계를 넘는 입력(중첩 20,000 초과)은 크래시가 아니라 "수식이 너무 복잡합니다" 오류로 끝납니다.
계산 실패는 예외가 아니라 오류 코드로 돌려줍니다. 타이핑 중에는 미완성 수식이 정상이라,
그 경로에서 예외를 만들면 키 입력마다 스택 트레이스 수집 비용이 붙기 때문입니다.

### 3. 화면 — 윈도우 렌더링

`ui/ExpressionRenderer.kt`

TextView 에 5,000 자를 넣으면 매번 그만큼 텍스트 레이아웃을 다시 계산합니다.
실제로 보이는 건 커서 주변 수십 자뿐이므로, 커서 기준 64 자만 잘라 넘기고
잘린 쪽은 `…` 로 표시합니다. 수식이 10 자든 10 만 자든 렌더링 비용이 같습니다.

버퍼에는 함수를 사설 사용 영역 문자 1개(U+E001 = sin …)로 저장하고 그릴 때만
`sin`, `π` 같은 이름으로 펼칩니다. 저장 공간은 1/4, 토큰 판별은 배열 조회 한 번입니다.

### 4. 계산 스레드

`ui/CalculatorViewModel.kt`

- 512 자 이하: UI 스레드에서 갭 버퍼를 **복사 없이** 바로 계산합니다(수십 µs).
- 512 자 초과: 90ms 디바운스 후 워커 스레드에서 계산합니다. 연속 타이핑 중에는
  파싱이 아예 돌지 않습니다.

워커에 넘기는 스냅샷 `CharArray` 는 `ScratchPool` 에서 최대 3개만 돌려씁니다.
전부 사용 중이면 그 틱의 미리보기를 건너뜁니다(다음 입력에서 다시 계산됨).
엔진 인스턴스도 UI 용/워커용으로 분리해 배열을 공유하지 않으므로 락이 필요 없습니다.

## 기능

- 사칙연산, 거듭제곱(오른쪽 결합), 괄호, 곱셈 생략(`2π`, `3(4+5)`, `(1)(2)`)
- 삼각/역삼각/쌍곡 함수, DEG/RAD/GRAD 전환 (DEG 에서 `sin(180)` 은 정확히 0, `tan(90)` 은 정의역 오류)
- `ln`, `log`, `log₂`, `logₐ(밑,진수)`, `exp`, `√`, `∛`, `abs`
- 계승 `x!`(감마 함수로 실수까지 확장), `%`, `x²`, `x³`, `x⁻¹`
- `mod(a,b)`, `nCr(n,r)`, `nPr(n,r)`
- `Ans`, 메모리(`MC`/`MR`/`M+`/`M−`), 계산 기록 30건(원형 버퍼)
- `2nd` 시프트(한 번 적용 후 자동 해제), 커서 이동 `◀ ▶`, `DEL` 길게 눌러 연속 삭제
- `=` 를 누르면 닫히지 않은 괄호를 자동으로 채우고 알려줍니다

## 테스트

`app/src/test/` 에 32개 단위 테스트가 있습니다. 계산 정확성뿐 아니라 설계 목표 자체를 검증합니다.

- 갭 버퍼: 1만 자 입력에 재할당 20회 미만, 갭이 가운데 있을 때의 복사 정확성, 입력 상한 처리
- 5,000 겹 괄호에서 `StackOverflowError` 없이 계산
- 한계를 넘는 중첩은 크래시 대신 `TOO_COMPLEX` 오류
- 4만 항짜리 수식(약 8만 자) 정확 계산
- 같은 엔진을 반복 사용해도 이전 계산의 잔재가 남지 않음

## 알려진 제약

- 입력 상한은 10만 자입니다. 넘으면 조용히 무시하고 토스트로 알립니다(OOM 대신).
- 붙여넣기로 들어온 `sin` 같은 ASCII 함수 이름은 인식하지 않습니다. 키패드 입력 전용입니다.
- `%` 는 "100으로 나누기"로 정의했습니다(`50%` = 0.5). `a + b%` 를 `a × (1 + b/100)` 으로
  해석하는 계산기도 있으나, 예측 가능한 쪽을 택했습니다.
